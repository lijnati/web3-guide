Changing the website is easy. Changing a deployed contract is not: you have to deploy a new one. Plan a little first.

## What goes on the blockchain?

Only put something on-chain if it must be **public, impossible to fake, or owned by users**. Everything else stays in the website or a normal backend.

| Put on-chain | Keep off-chain |
| --- | --- |
| Balances, ownership, votes, payments | Images, videos, long text (save a link instead) |
| Rules everyone must trust ("max 100 per wallet") | Search, sorting, filtering |
| Records that must be permanent | Private data |
| Small values: numbers, addresses, short text | Data that changes many times a second |

<Callout type="warn" title="Nothing on-chain is private">
  Anyone can read everything on the blockchain, even variables marked `private`. Never store passwords, secrets or personal data.
</Callout>

## Design the functions first

List your contract's functions like you would plan a REST API:

| Kind | In Solidity | Costs gas? | Needs a wallet? | Example |
| --- | --- | --- | --- | --- |
| Read | `view` function or `public` variable | No | No | `value()` |
| Write | `external` function | Yes | Yes | `setValue(uint256)` |
| Write + pay | `external payable` | Yes, plus the ETH sent | Yes | `buy()` |
| Event | `event` + `emit` | Part of a write | — | `ValueChanged(by, newValue)` |
| Error | `error` + `revert` | — | — | `ZeroValue()` |

Then answer three questions:

- **Who can call each write?** Anyone, only the owner, or some addresses.
- **When should a call fail?** Each rule becomes an error and a test.
- **What does the contract need at the start?** These become constructor arguments.
